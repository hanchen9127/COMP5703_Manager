## A. The ticket as written (Jira, 08/10)

"Verify first, then close or build the gap":
1. Check each criterion on `main` and record the result on the ticket:
   - a task can be created under a project, choosing annotation or judgement and the task type;
   - the task records what a finished result looks like: labels for annotation, a verdict plus reasoning for judgement;
   - text tasks work end to end, and image and video tasks can be created without breaking.
2. If all hold, close the ticket.
3. If not, build only the gap. The likely one: `label_schema_ref` is a string only the AI batch reads, so a finished
   result isn't checked against a shape. Then a judgement task should reject a result with no verdict, and an annotation
   task one whose labels aren't in its definitions, with a test each.

**What's known already** (from the [judgement-task report](../analysis/2026-10-08-judgement-task-explained.md), §8):
- the API doesn't refuse a judgement without a `verdict` or `rationale`; only the web panel does;
- story C5 also requires the rationale on judgement results, "required, not an optional comment box".

## B. Added 08/10: the required-annotators count on the task form (story D8, subtask 2)

**Why:** story D8 subtask 2, "Add a required-annotators count to the task, chosen at creation". SCRUM-48 (Kanishka) built
it on the API only ("ONLY BACKEND"), and no D8 ticket added it to the web. So no task can have two annotators per item
from the app: the create form never sends `required_annotators`, so every task gets 1. Client answer (17 Sep): "the
number of annotators an item needs is chosen when the task is created".

**Today on `main`:**

| | State |
| --- | --- |
| API create (`TaskCreate.required_annotators`, 1–10, default 1) | ✅ |
| Enforcement: submission limit, queue, completion | ✅ (SCRUM-48) |
| API edit (`TaskUpdate`) | ❌ not accepted |
| Web create form | ❌ no field |
| Web task Setup (show and edit) | ❌ |
| Web queues ("2 of 3") | ✅ (SCRUM-93) |

**Scope to add:**
1. **Web, create form:** a "Required annotators" number field (1–10, default 1), sent with the task.
2. **API, edit while a draft:** `TaskUpdate.required_annotators`, with these rules:
   - changing it on a task that has left draft → 409, as SCRUM-87 does for the annotation mode;
   - resending the same value → accepted, because the setup card resends every field;
   - the range checked as at creation.
3. **Web, task Setup:** show the count, editable while the task is a draft and read-only after activation, saying why.
4. **Docs Sync:** `api_surfaces.md` (the update contract).
5. **Tests:**
   - API: a draft task's count can change, and activation then enforces the new count; an active task's change → 409;
     the same value is accepted; out of range → 422;
   - web: the form sends the field; Setup disables it after activation.
