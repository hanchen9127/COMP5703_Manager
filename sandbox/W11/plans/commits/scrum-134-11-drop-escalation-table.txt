refactor(api): drop the task_item_escalations table (SCRUM-134)

Since the previous commit nothing writes or reads task_item_escalations:
route_escalation, its only writer, is gone, and so is every read. A fresh
seed holds no rows. The model, the table and what kept the table's
columns up to date go with it.

db_models.py: TaskItemEscalationDB goes. No relationship, backref or
index outside the class pointed to it, so nothing else in the models
changes, and create_all no longer creates the table.

database.py:
- migrate_db_schema loses its task_item_escalations branch, which added
  resolution_outcome and accepted_annotation_id to an older SQLite table.
  The rest of the SQLite schema helper is untouched.
- reset_db drops task_item_escalations before Base.metadata.drop_all,
  beside the two unmapped intake tables, and their comment now covers all
  three. The metadata drop only knows mapped tables. A database written
  before #102 still holds the table, and its foreign key to task_items
  blocks dropping task_items while a row references it: on SQLite with
  foreign keys on (the application engine turns them on) the drop fails
  with "FOREIGN KEY constraint failed", and PostgreSQL refuses to drop a
  table another table references. The decided path for such a database is
  init_data.py --reset, so the reset must clear the table itself.
  DROP TABLE IF EXISTS does nothing on a database that never had it.

db_schema_blueprint.md: the table leaves the judgment table list, and its
section goes. ADR 013 still names the table and the model, as the
history of the decision.

Why it is safe: nothing in the application read or wrote the table, no
route or response named it, and no workflow or story behaviour changes.
A database written before #102 is reset, as decided, and the reset now
handles the leftover table.
