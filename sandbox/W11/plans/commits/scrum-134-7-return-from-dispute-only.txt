refactor(api): an expert's Return is read only from the dispute's decision (SCRUM-134)

An expert's Return is a dispute decision. The replacement guard, the
item aggregate and the annotate queue read it from the dispute, as a
round outcome of returned.

They also read a second, legacy kind of Return evidence:
TaskItemEscalationDB rows and escalation_decided audits. Only
route_escalation and decide_escalation write those, and no route
reaches either: both routes answer 410. A fresh seed holds none of
them. So the legacy evidence is always empty, and it goes.

task_item_status_resolution.py goes as a whole:
current_expert_return_at, current_expert_return_at_by_submission,
_audit_send_back_timestamps, _counts_after_reopen,
_latest_reopen_at_by_item, the legacy draft-chain matching,
_parse_audit_json and the constants. Nothing else imported it.

Each caller now does what it did when the evidence was empty:
- assert_submission_may_be_replaced: sent_back was always false, so
  the second may_resubmit call and the time comparison go.
- item_status_after_accept: a held round keeps the item disputed. The
  branch that turned Return evidence into returned goes, and so does
  its docstring sentence.
- the annotate queue: rework reads may_resubmit on the round outcome
  alone.

may_resubmit loses its sent_back keyword, which only this evidence set:
it now allows a returned or rejected round and nothing else.

The audit log index comment no longer names the Return evidence
lookups. Open item escalations still hold an item; a later commit
removes them.
