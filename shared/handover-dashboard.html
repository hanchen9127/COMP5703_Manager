        Conventions

        Conventions you can keep or replace

        This is how the team worked. None of it is imposed on you. Keep what helps and replace the rest with your own.

        1. Pull requests into main, reviewed by someone else. The review and its verdict stay on the PR. main is not protected on our GitHub plan, so this is an agreement, not a control.
        2. Merge commits, never squash. Branches are merged into one another, so squashing would duplicate history. Sync by merging main into your branch, not by rebasing a shared one.
        3. Personal branches named CS57-<Name> with an optional topic, for example CS57-Hanchen-ai-integration. Use your own prefix.
        4. PR titles read type(scope): description (stories, tickets), for example feat(api): refuse a release that fails its pre-release checks (H3, SCRUM-105). Types: feat, fix, docs, test, refactor, perf. Scopes: api, web, evaluation, seed, db, ci, docs.
        5. One coherent, reviewable commit per unit of change. The body says what was wrong, then what changed, and ends with the story or issue.
        6. Run npm run check and the casebook before asking for review, and say so in the PR. CI runs the backend suite and web checks on each non-draft PR, and PostgreSQL after each merge to main.
        7. Tests ship in the same change. A defect fix comes with a test that fails against the old behaviour; separate the tests that prove the fix from the guards that stop it going too far.
        8. Update the docs in the same change as any state, route or data-model change (the state model and the API contract live under docs/design).
        9. Write each design decision as a numbered ADR in docs/adr with status, date, author, stories and PR.
        10. Give every story its own casebook cases. Each run is compared with the committed baseline; the harness drives the real API with real logins and roles.
